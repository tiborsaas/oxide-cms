Headless content, embedded in your Rust binary.
Axum · SQLite · JWT · CommonMark. No daemon. No config. No templates.

main.rs[ 12 LINES / ONE ROUTER ]
// Cargo.toml:  oxide-cms, axum, tokio
use oxide_cms::{api_router, init_db, list_articles, AppConfig, AppState};

#[tokio::main]
async fn main() {
    let config = AppConfig::from_env();
    let pool   = init_db(&config.database_url).await.unwrap(); // migrates itself

    // read straight from the pool: zero HTTP, zero serialization overhead
    let posts = list_articles(&pool, Some(10), None).await.unwrap();

    // full REST API (posts, categories, tags, auth) in one line
    let app = axum::Router::new()
        .nest("/api", api_router())
        .with_state(AppState { pool, config });

    axum::serve(tokio::net::TcpListener::bind("0.0.0.0:3000").await.unwrap(), app).await.unwrap();
}

WHY

[01] EMBEDDEDA library, not a service. Call content functions directly from your handlers; no network hop between app and CMS.
[02] FAST BY DEFAULTSQLite in WAL mode, indexed slugs and relations, batched tag loading. No N+1 queries.
[03] HEADLESSYou own the frontend. Content is JSON and Markdown; render with whatever you like.
[04] ZERO CONFIGPoint at a file. Tables and indexes are created on first connect.
[05] SINGLE FOCUSOxide focuses on doing one thing right only: serving content fromt SQLite.
[06] AGENTIC BY NATUREProvides an MCP endpoint too so that content editing can be seamless.

API SURFACE

list_articles(&pool, limit, offset) published posts, paginated
get_article_by_slug(&pool, slug) single post with category + tags
list_articles_by_category(&pool, slug, ..) filter by category
list_articles_by_tag(&pool, slug, ..) filter by tag
list_categories / list_tags taxonomies
markdown_to_html(&content) CommonMark, tables, task lists
api_router() mountable REST: /posts /categories /tags /auth
